# AI 자산관리 리포트 — 기능 스펙

> **문서 목적**: 백엔드(FastAPI) 설계·구현을 위한 **기능 요구사항** 정의서.
> 스키마 설계, 테이블 구조, 프롬프트 문안, 라이브러리 선택 등 **기술 설계는 이 문서 범위 밖**이며 백엔드 프로젝트에서 결정한다.
> 이 문서는 "무엇을 만들어야 하는가"와 "어떤 규칙을 지켜야 하는가"만 규정한다.

작성일: 2026-08-07
클라이언트: Flutter 가계부 앱 (`flutter_account_book_vibe`)

---

## 1. 개요

기존 가계부 앱은 카테고리별 지출, 구성원별 지출, 월별 추이 같은 **집계 화면**을 제공한다.
이 기능은 그 위에, 축적된 가계부·자산 데이터를 LLM이 해석해서 **매월 한 편의 조언 글**을 발행하는 것이다.

핵심 컨셉은 **"친한 자산/재무 관리자"** 다. 지표 나열 리포트가 아니라, 내 사정을 아는 사람이 내 돈 상황을 보고 평가하고 조언해주는 글이다.

### 지표 리포트와의 차이

| | 기존 집계 화면 | 이 기능 |
|---|---|---|
| 방향 | 데이터를 그대로 보여줌 | 해석하고 판단함 |
| 기억 | 없음 | 지난 회차 맥락을 기억 |
| 범위 | 데이터 안에서만 | 데이터에 없는 건 사용자에게 물어봄 |
| 태도 | 중립 | 편들되 봐주지 않음 |
| 형식 | 고정 차트 | 매달 다른 얘기 |

### 이 기능이 성공했다고 볼 수 있는 상태

- 사용자가 매달 발행 버튼을 누른다 (읽을 가치가 있다는 신호)
- 3개월 뒤 리포트가 첫 달보다 구체적이다 (프로필 축적이 작동한다는 신호)
- 리포트에 등장하는 숫자가 앱의 집계 화면 숫자와 일치한다

## 2. 용어

| 용어 | 정의 |
|---|---|
| **회차(period)** | 리포트 1건이 다루는 기간. `YYYY-MM` 형식, 분석 대상 월. 예: `2026-09` 회차는 2026년 9월 데이터를 다루며 2026년 10월에 처리된다 |
| **프로필** | 사용자에 대해 누적된 맥락을 담은 텍스트. 3개 구역으로 나뉜다 |
| **질문** | 데이터만으로 판단할 수 없는 것에 대해 LLM이 사용자에게 던지는 물음 |
| **발행** | 특정 회차의 리포트를 생성해서 저장하는 행위 |
| **관리자** | 리포트를 쓰는 화자(persona). LLM이 연기하는 역할 |

## 3. 전체 흐름

```
[0] 초기 프로필 세팅        수기      최초 1회
        ↓
[1] 질문 생성               배치      매월 1일
        ↓
[2] 질문에 답변             수기      선택, 아무 때나
        ↓
[3] 리포트 발행             API 호출  사용자가 앱에서 버튼
        ↓
[4] 앱에서 열람             API 조회
        ↓
      다음 달 [1]로
```

### 단계별 설명

**[0] 초기 프로필 세팅 (수기, 최초 1회)**
사용자가 자기 목표·사정·성향을 직접 적는다. 이게 없으면 첫 리포트가 일반론에 그친다.

**[1] 질문 생성 (배치, 매월 1일)**
전월 가계부·자산 데이터와 현재 프로필을 읽고, LLM이 **질문만** 생성해서 저장한다.
이 단계에서는 리포트를 만들지 않고 프로필의 관찰 구역도 갱신하지 않는다.

**[2] 답변 (수기, 선택)**
사용자가 질문을 보고 프로필의 사용자 확정 구역에 답을 적는다.
**답하지 않아도 된다.** 답 없으면 [3]에서 LLM이 가정을 세워 진행한다.

**[3] 리포트 발행 (사용자 액션)**
앱의 발행 버튼 → API 호출. 답변이 반영된 프로필과 최신 데이터로 LLM이 리포트를 쓰고, 동시에 프로필의 관찰 구역을 갱신한다.

**[4] 열람**
앱이 리포트를 조회해 표시한다.

### 왜 질문 생성과 발행을 나누는가

한 번의 호출로 리포트와 질문을 같이 만들면, 그 질문에 대한 답은 **다음 달 리포트에나 반영된다**. 답변이 한 달씩 밀린다.
둘로 나누면 답변이 같은 회차 리포트에 즉시 반영되어, 사용자는 처음 읽는 순간부터 완성된 리포트를 본다.

## 4. 프로필

사용자에 대한 누적 맥락. 텍스트 형태이며 **3개 구역**으로 구성된다. 구역마다 쓰는 주체가 다르고, 이 경계가 이 기능의 안전장치다.

| 구역 | 쓰는 주체 | 쓰는 시점 | 갱신 방식 |
|---|---|---|---|
| **사용자 확정** | 사용자 | 수기, 아무 때나 | 사용자가 직접 편집 |
| **미답변 질문** | LLM | 질문 생성 배치 | 전면 교체 |
| **관찰** | LLM | 리포트 발행 | 전면 교체 |

### 구역별 내용

**사용자 확정** — 사용자가 사실로 확인해준 것. 목표, 생활 사정, 성향, 질문에 대한 답.
```
- 목표: 전세보증금 1.5억 · 2028년
- 월 지출 상한 300만 (소비만, 투자 별도)
- 배우자 육아휴직 중, 12월 복직 예정
- 잔소리 세게 해도 됨
- 2026-09 여행 87만, 일회성
```

**미답변 질문** — 이번 회차에 LLM이 궁금한 것.
```
- Q1. 9/12~15에 식비·교통·숙박으로 흩어진 87만, 여행이었어?
      일회성인지에 따라 상한 초과 판정이 뒤집혀.
- Q2. 월 지출 상한 300만은 투자·저축 제외한 순수 소비 기준이야?
```

**관찰** — LLM이 데이터에서 파악한 것과 자기 판단 이력.
```
- 9월 소비 254만(여행 87만 제외), 상한 300만 내
- 고정비 41%→47%. 11일 4.9만 / 19일 1.2만 신규 반복결제
- 11일 4.9만: 2회 문의 무응답 → 유지 고정비로 가정하고 진행
- 틀린 추측: 6월 "차 구입" 추정 → 실제로는 렌트 보증금
```

### 요구사항

- **R4-1**: 사용자 확정 구역은 LLM이 어떤 경로로도 변경할 수 없어야 한다. LLM 출력이 이 구역을 포함할 수 없는 구조여야 한다(출력 필드 자체를 분리).
- **R4-2**: 미답변 질문 / 관찰 구역은 매 갱신 시 **전면 교체**한다. 부분 병합하지 않는다. 해소된 항목은 LLM이 다시 쓰지 않는 것으로 자연스럽게 사라진다.
- **R4-3**: 관찰 구역에는 **사용자가 확인해준 사실과 LLM의 추측이 구분되어** 기록되어야 한다. 추측이 사실로 굳어지는 오염을 막는다.
- **R4-4**: LLM이 과거에 틀린 추측을 했다면 그 사실이 관찰 구역에 남아야 한다. 같은 오판을 반복하지 않기 위함이다.
- **R4-5**: 프로필은 항상 1개(사용자당 1개)다. 회차별로 나뉘지 않는다. 단, 발행 시점의 프로필 스냅샷은 해당 리포트에 함께 보존한다(사후 검증용).
- **R4-6**: 프로필 전체 분량은 관리 가능한 수준으로 유지되어야 한다. 관찰 구역이 무한히 길어지면 LLM이 오래된 항목을 정리하도록 한다.

## 5. 기능 요구사항

### F1. 질문 생성 (배치)

**트리거**: 매월 1일 자동 실행
**대상 회차**: 전월

- **F1-1**: 전월 회차의 가계부·자산 데이터와 현재 프로필을 입력으로 LLM을 호출해 질문 목록을 생성한다.
- **F1-2**: 생성된 질문으로 프로필의 미답변 질문 구역을 교체한다.
- **F1-3**: 이 단계에서 리포트를 생성하지 않고, 관찰 구역도 건드리지 않는다.
- **F1-4**: 질문은 **최대 2개** (첫 회차는 예외, F5-1 참조). 물을 게 없으면 0개도 정상이다.
- **F1-5**: 질문은 각각 **왜 묻는지**를 포함해야 한다. "이 답에 따라 판단이 어떻게 달라지는지"를 사용자가 알아야 답할 동기가 생긴다.
- **F1-6**: 이미 사용자 확정 구역에 답이 있는 내용은 다시 묻지 않는다.
- **F1-7**: 같은 질문을 **2회차까지만** 반복한다. 3회차부터는 묻지 않고, 관찰 구역에 "무응답 → 어떤 가정으로 진행" 을 기록한다.
- **F1-8**: 직전 회차 리포트가 미발행 상태면, 답변 없는 상태로 먼저 발행한 뒤 이번 회차 질문 생성을 진행한다. 사용자가 발행 버튼을 계속 안 눌러도 루프가 멈추지 않아야 한다.
- **F1-9**: 같은 회차에 대해 중복 실행되지 않아야 한다. 재실행 시 기존 질문을 교체한다.

### F2. 답변 저장 (수기)

- **F2-1**: 사용자가 프로필의 사용자 확정 구역을 직접 편집해 답을 적는다.
- **F2-2**: **앱에서 답변을 입력하는 기능은 만들지 않는다.** 앱은 질문을 보여주기만 한다.
- **F2-3**: 답변은 선택 사항이다. 답하지 않아도 다음 단계가 정상 동작해야 한다.

### F3. 리포트 발행

**트리거**: 사용자가 앱에서 발행 버튼을 누름 (`POST`)

- **F3-1**: 지정된 회차의 가계부·자산 데이터와 현재 프로필(답변 반영 상태)로 LLM을 호출해 리포트를 생성한다.
- **F3-2**: 같은 호출에서 갱신된 관찰 구역을 함께 받아 프로필에 반영한다. 별도의 프로필 갱신 호출을 두지 않는다.
- **F3-3**: 발행 시점의 프로필 스냅샷을 리포트와 함께 보존한다.
- **F3-4**: **재발행을 허용한다.** 같은 회차로 다시 호출하면 기존 리포트를 덮어쓴다. 사용자가 답을 추가로 적고 다시 발행하는 것이 정상 사용 흐름이다.
- **F3-5**: 리포트에 등장하는 합계 숫자는 시스템이 계산한 값과 일치해야 한다. LLM이 직접 산술 계산해서 얻은 값을 쓰지 않는다.
- **F3-6**: 발행은 시간이 걸리는 작업이다. 앱이 무한정 기다리지 않도록 진행 상태를 알 수 있어야 한다.
- **F3-7**: LLM 호출 실패 시 기존 리포트와 프로필이 손상되지 않아야 한다. 실패하면 이전 상태가 그대로 유지된다.
- **F3-8**: 아직 종료되지 않은 월(진행 중인 달)은 발행 대상이 아니다.

### F4. 조회

- **F4-1**: 리포트 목록 조회 — 회차, 헤드라인, 발행 시각. 최신순.
- **F4-2**: 리포트 상세 조회 — 회차 지정.
- **F4-3**: 현재 상태 조회 — 이번에 발행할 수 있는 회차, 미답변 질문 목록, 발행 여부. 앱의 배너와 버튼 상태를 결정한다.

### F5. 첫 회차 처리

- **F5-1**: 프로필의 관찰 구역이 비어 있는 첫 회차에는 질문을 **최대 3개**까지 허용한다.
- **F5-2**: 첫 회차는 과거 데이터를 통상보다 길게 참조해 맥락을 확보한다.
- **F5-3**: 초기 프로필(사용자 확정 구역)이 완전히 비어 있어도 동작해야 한다. 단 리포트가 일반론에 그치는 것은 감수한다.

## 6. 리포트 내용 요구사항

### 6.1 구조

리포트는 **고정 골격 + 자유 본문**의 혼합이다. 전부 자유면 매달 형식이 달라 비교가 안 되고, 전부 고정이면 LLM을 쓰는 의미가 없다.

**고정 요소 (매 회차 동일, 추이 비교용)**

| 요소 | 내용 |
|---|---|
| 헤드라인 | 이번 달을 한 문장으로. 결론부터 |
| 핵심 지표 4개 | 순저축 / 순자산 / 고정비율 / 비상자금 개월수. 각각 값 + 전월 대비 증감 + 좋음·주의 판정 |
| 액션 | **정확히 1개**. 이번 달에 할 일 |

**자유 요소 (매달 다름)**

본문은 마크다운. LLM이 이번 달 데이터를 보고 **가장 할 말이 있는 주제 2~4개**를 스스로 골라 쓴다. 어떤 달은 여행 지출 분석이고, 어떤 달은 태깅 품질 지적이고, 어떤 달은 구독 정리다. 섹션 제목과 개수를 고정하지 않는다.

본문 말미에 미답변 질문이 포함된다.

**핵심 지표 4개 정의**

| 지표 | 정의 |
|---|---|
| 순저축 | 해당 월 수입 − 지출 |
| 순자산 | 해당 월말 순자산 평가액 |
| 고정비율 | 고정비 합 ÷ 수입 |
| 비상자금 개월수 | 현금화 가능 자산 ÷ 최근 3개월 평균 지출 |

### 6.2 화자 규칙 (관리자 페르소나)

**이 절이 이 기능의 품질을 결정한다.** LLM의 기본 성향은 칭찬과 완충이고, 그대로 두면 3개월 안에 아무도 안 읽는 격려문이 된다. 친한 관리자의 가치는 **다른 사람은 해주지 않는 말을 해주는 것**이다.

- **P-1**: 결론부터 쓴다. 서론·배경 설명으로 시작하지 않는다.
- **P-2**: 나쁜 소식을 먼저, 좋은 소식을 나중에 쓴다.
- **P-3**: **칭찬은 회차당 최대 1개.** 숫자 근거나 이전 회차 약속 이행이라는 근거가 있을 때만. 근거 없으면 생략한다.
- **P-4**: "잘하고 계세요", "훌륭합니다" 같은 근거 없는 격려를 쓰지 않는다.
- **P-5**: **지적도 회차당 1개.** 문제를 여러 개 발견해도 가장 중요한 하나만 쓴다. 여러 개를 지적하면 아무것도 실행되지 않는다.
- **P-6**: 확신이 없으면 추측을 사실처럼 쓰지 않는다. 질문으로 넘긴다.
- **P-7**: 사용자의 변명에 무조건 수긍하지 않는다. "이번 달은 특수했다"는 주장이 프로필이나 데이터로 확인되지 않으면 그렇게 말한다.
- **P-8**: 이전 회차에 사용자가 한 약속이 지켜졌는지 확인하고 언급한다. 2회 연속 미이행이면 목표 자체를 재조정하자고 제안한다.
- **P-9**: 판단 근거를 보여준다. "왜 그렇게 생각했는지"를 날짜와 금액으로 인용한다.
- **P-10**: 말투는 프로필의 성향 항목을 따른다. 다만 **말투가 아니라 기억·되묻기·봐주지 않음이 "친함"의 실체**다. 반말만 쓰는 리포트는 목적을 달성하지 못한다.

**금지 사항**

- **P-11**: **특정 종목·상품 매매 추천 금지.** 자산 데이터에 종목 정보(ticker)가 포함되어 LLM이 자연스럽게 종목 얘기로 흐를 수 있다. 명시적으로 차단해야 한다.
  - 허용: 자산군 배분 편중, 환노출 비중, 현금 비중, 유동성 수준
  - 금지: "○○ 사라/팔라", 특정 상품 수익률 전망, 시장 전망 단정
- **P-12**: 계산하지 않은 숫자를 쓰지 않는다. 시스템이 제공한 집계값을 인용하고, 그 외의 수치는 근사치임을 밝힌다.

## 7. 분석 소재

LLM에게 "알아서 잘 분석해라"만 주면 매달 같은 소리를 한다. 아래는 **이 데이터셋에서만 나올 수 있는 소재**이며, LLM이 참고할 후보로 제공되어야 한다. 단 매달 전부 다루는 체크리스트가 아니라, 그 달에 해당하는 것만 고르는 재료 목록이다.

### 7.1 사용자가 이미 태깅했지만 아무도 안 보는 데이터

앱은 아래 필드를 **입력받고 있지만 어떤 화면에서도 분석에 쓰지 않는다.** 추가 입력 요구 없이 바로 쓸 수 있는 가장 값싼 소재다.

| 필드 | 의미 | 뽑을 수 있는 것 |
|---|---|---|
| `impulseYn` | 충동구매 여부 (사용자 직접 태깅) | 충동 지출 비중·추이, 유발 카테고리, 결제수단과의 상관, 요일 패턴, "충동 없었으면 순자산 얼마" 반사실 |
| `fixedPriceYn` | 고정비 여부 | 고정비 비율, **고정비 상승 감지**(한 번 오르면 잘 안 내려가므로 경보 가치 최상) |
| `pointPrice` | 포인트 사용액 | 실질 할인율, 카테고리별 포인트 회수 편차 |
| `cashableYn` | 현금화 가능 자산 | 비상자금 개월수, 유동성 수준 |
| `exchangeRateYn` | 환율 연동 자산 | 환노출 비중, 순자산 증감 중 환율 기여분 분리 |
| `remark` | 자유 메모 | **유일한 비정형 소스.** 규칙 기반으로는 못 읽음. 지출의 성격·맥락 추론 |

### 7.2 가계부 × 자산 결합 지표

두 도메인을 함께 보는 것이 이 앱의 고유한 강점이다.

- **비상자금 커버 개월수** — 현금화 가능 자산 ÷ 최근 3개월 평균 지출
- **저축률 vs 순자산 갭** — 장부상 저축액과 실제 순자산 증가분의 차이. "3개월간 300만 저축했는데 순자산은 180만 늘었다"는 다른 어떤 지표도 못 잡는 신호다
- **환노출 비중** 및 순자산 증감 중 환율 변동 기여도
- **목표 도달 예상 시점** — 현재 저축 페이스 기준

### 7.3 LLM이라서 가능한 것 (규칙 기반으로 원천 불가)

- **카테고리 경계를 넘는 사건 묶기** — 7/12~15에 식비·교통·숙박·쇼핑에 흩어진 14건을 "여행 1건, 87만"으로 인식. 집계는 카테고리 축에 갇혀 있어 절대 볼 수 없다. **가장 큰 차별점.**
- **메모 독해로 생활 맥락 추론** — "이사 관련 지출 3건 감지, 일시적. 다음 달 기저효과 주의"
- **사용자 태깅 품질 감사** — "충동으로 태깅 안 했지만 패턴상 충동으로 보이는 6건"
- **이상함의 기준을 매달 새로 정함** — 고정 임계값이 아니라 "총액은 평범한데 구성이 뒤집혔다"처럼 보는 축 자체를 바꿈
- **상호명 표기 흔들림 흡수** — 메모의 "스벅"/"스타벅스"/"STARBUCKS"를 정규화 규칙 없이 묶음
- **반사실 시나리오** — "배달을 주 1회로 줄이면 연 210만, 비상자금 4.2→5.1개월"
- **회차 간 연속성** — "지난달 지적한 구독 3건 중 2건 해지 확인, 1건 잔존"

## 9. API

앱이 사용하는 인터페이스. 경로·형식은 백엔드에서 확정하되, 아래 **역할과 응답에 담겨야 할 정보**는 충족해야 한다.

### A1. 리포트 목록 조회 (GET)

앱의 리포트 아카이브 화면.

담아야 할 정보: 회차, 헤드라인, 발행 시각. 최신순 정렬. 페이지네이션.

### A2. 리포트 상세 조회 (GET)

회차를 지정해 리포트 1건을 가져온다.

담아야 할 정보:

| 필드 | 용도 |
|---|---|
| 회차 | |
| 발행 시각 | |
| 헤드라인 | 상단 한 문장 |
| 핵심 지표 4개 | 각각 라벨 / 값 / 전월 대비 증감 / 판정(좋음·주의·나쁨) / 표시 형식(금액·퍼센트·개월) |
| 본문 | 마크다운. 앱은 렌더만 함 |
| 액션 | 1개. 앱에서 강조 배너로 표시 |

지표의 판정과 표시 형식은 백엔드가 내려준다. **앱에 판정 로직을 두지 않는다.**

### A3. 리포트 발행 (POST)

회차를 지정해 리포트를 생성/재생성한다.

- 이미 발행된 회차를 다시 호출하면 덮어쓴다 (F3-4)
- 진행 중인 월은 거부한다 (F3-8)
- LLM 호출이 오래 걸리므로 앱이 결과를 기다리는 방식을 정의해야 한다 (동기 응답 + 충분한 타임아웃, 또는 비동기 접수 후 상태 폴링). 어느 쪽이든 앱이 **진행 중 / 완료 / 실패**를 구분할 수 있어야 한다 (F3-6)
- 동시에 두 번 호출되어도 중복 생성되지 않아야 한다
- 실패 시 기존 데이터가 손상되지 않아야 한다 (F3-7)

### A4. 현재 상태 조회 (GET)

앱의 홈 배너와 발행 버튼 상태를 결정한다.

담아야 할 정보:

| 필드 | 용도 |
|---|---|
| 발행 가능 회차 | 버튼이 어느 회차를 발행할지 |
| 발행 여부 / 발행 시각 | 버튼 문구를 "발행"과 "다시 발행" 중 선택 |
| 미답변 질문 목록 | "답변할 질문 2개가 있어요" 배너. **표시 전용, 입력 UI 없음** |
| 진행 중 여부 | 발행 작업이 돌고 있으면 버튼 비활성 |

## 10. 앱 측 범위 (참고)

백엔드 구현 범위는 아니지만, 인터페이스 합의를 위해 명시한다.

앱이 만드는 것:
- 리포트 상세 화면 — 지표 카드 4개 + 마크다운 본문 + 액션 배너
- 리포트 목록 화면
- 발행 버튼 + 미답변 질문 안내 배너

앱이 만들지 않는 것:
- 질문 답변 입력 UI (수기로 처리)
- 지표 계산 및 판정 (백엔드가 값과 판정을 함께 내려줌)
- 프로필 편집 UI

## 11. 제약과 한계

설계 시 전제로 삼아야 할 사항.

| 항목 | 내용 | 영향 |
|---|---|---|
| **예산 필드 없음** | 가계부에 budget 개념이 없다 | "예산 대비 초과" 류 분석 불가. 기준선은 과거 평균, 또는 사용자가 프로필에 적은 상한뿐 |
| **거래 시각 없음** | 날짜만 기록된다 | "심야 충동구매" 같은 시간대 분석 불가. 요일 분석은 가능 |
| **가맹점명 없음** | 상호명 필드가 없다 | 메모에 적혀 있는 경우에만 LLM이 부분적으로 파악 |
| **LLM 산술 오류** | LLM은 사칙연산을 자주 틀린다 | 리포트 숫자는 시스템 계산값 기반이어야 한다 (F3-5) |
| **재현성 없음** | 같은 입력으로 두 번 돌리면 다른 글이 나온다 | 발행된 리포트는 저장해서 고정한다. 화면에서 매번 생성하지 않는다 |
| **원장 외부 전송** | 거래 내역 전체가 LLM API로 전송된다 | 개인용 서비스 전제. 다중 사용자로 확장 시 재검토 필요 |
| **사용자 이탈** | 발행 버튼을 안 누르면 루프가 멈춘다 | F1-8로 자동 발행 처리 |

- 주간 리포트 — 회차 표기만 바꾸면 확장 가능하도록 열어두되, 지금은 월간만

- 대화형 질의응답 (원장이 컨텍스트에 들어가므로 향후 저렴하게 추가 가능하지만 이번 범위 아님)
- 푸시 알림
- 다중 사용자 / 권한 분리

## 13. 구현 순서 제안

1. 리포트 조회 API (A1, A2) — 더미 데이터로 앱과 인터페이스 먼저 합의
2. 리포트 발행 (F3, A3) — 프로필 없이도 동작하는 최소 버전
3. 프로필 3구역 및 관찰 구역 갱신 (R4 요구사항)
4. 질문 생성 배치 (F1)와 상태 조회 (A4)
5. 첫 회차 처리 및 자동 발행 (F1-8, F5)

1~2번만 되어도 앱은 리포트를 보여줄 수 있다. 3번부터가 "친한 관리자"가 되는 부분이다.
